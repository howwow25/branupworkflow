# 같은 SQLite 에 쓰는 쪽이 둘이다 — 굽기는 읽기만, 쓰기는 줄 세우기

ADR 0001 로 반복 보충(쓰기)을 `dashboard_html.py` 에 넣었는데, 그 스크립트는
`api_server` 가 **변경마다 띄우는 별도 프로세스**다. 그래서 같은 DB 에 쓰는
프로세스가 둘이 되었고, 업무를 연달아 만들면 `database is locked` 로 요청이
**응답 없이 끊겼다** (화면에는 "API 서버 연결 실패" 만 떴다). 12개 동시 생성
시험에서 12개 전부 실패했다.

네 가지를 바꿨다.

**굽기는 읽기만 한다.** `api_server` 가 굽기를 띄울 때 `BRANUP_SKIP_BACKFILL=1`
을 준다. 보충은 API 서버가 자기 쪽에서 하므로 잃는 것이 없다. `update.ps1` 이
굽기를 직접 돌릴 때는 그 변수가 없으니 보충이 그대로 된다.

**스키마 확인은 한 번만.** 전에는 `get_conn()` 마다 `CREATE TABLE`·`ALTER
TABLE`·`UPDATE` 를 돌렸다. 그 말은 **읽기만 하려는 연결도 쓰기 잠금을 잡는다**는
뜻이다. `PRAGMA user_version` 으로 최신인지 보고, 최신이면 아무것도 쓰지 않는다.
→ **칼럼이나 표를 더할 때마다 `db.SCHEMA_VERSION` 을 1 올려야 한다.** 안 올리면
새 마이그레이션이 영원히 돌지 않는다.

**`busy_timeout` 을 맨 먼저 건다.** `PRAGMA journal_mode=WAL` 을 먼저 두면 그
PRAGMA 자체가 기다리지 않고 터져서, 잠금 오류가 **연결을 만드는 단계**에서 난다.

**한 프로세스 안에서 쓰기는 직렬로.** `api_server` 는 요청마다 스레드를 쓴다.
사람 둘이 동시에 업무를 만들면 두 스레드가 같은 잠금을 다툰다. `db.py` 의 쓰기
함수에 `@_writer`(프로세스 전역 RLock)를 달아 줄을 세운다. 프로세스 밖은
`busy_timeout` 이 기다려 준다.

## Considered Options

**`busy_timeout` 만 올린다.** 가장 작은 변경이고 처음 시도한 것이다. 효과가
없었다 — 12 스레드로 격리 시험을 하면 `busy_timeout` 은 정상 작동하므로,
원인은 단순 쓰기 경합이 아니라 **읽기 경로까지 쓰기 잠금을 잡는 DDL** 과
**프로세스 여러 개**였다.

**MySQL 로 옮긴다.** 같은 서버에 이미 MySQL(`bpms`)이 있다. 하지만 이 앱은
표준 라이브러리만 쓰는 것이 특징이고, 옮기는 비용이 문제의 크기에 비해 크다.

**굽기를 없애고 화면을 매번 API 로 그린다.** 구조가 단순해지지만 정적 HTML 로
굽는 것이 이 앱의 뼈대다(ADR 0001 이전부터). 이번 문제의 범위를 넘는다.

## Consequences

사람 7명 규모에서 쓰는 도구라 쓰기 직렬화의 성능 비용은 보이지 않는다. 쓰기가
길어지는 작업(`backfill_series` 가 회차 4개를 만드는 정도)에서도 수 밀리초다.

`@_writer` 는 업무·반복 쓰기 경로에만 달려 있다. 프로젝트·파일 쓰기는 전부터
경합이 없던 경로라 건드리지 않았다 — 나중에 그쪽에서 같은 증상이 보이면 같은
데코레이터를 달면 된다.

`_SCHEMA_READY` 는 프로세스마다의 플래그다. 한 프로세스가 도는 중에 DB 파일을
지우고 다시 만들면 스키마가 다시 올라가지 않는다. 시험은 프로세스마다 새 DB 를
쓰므로 문제가 없고, 운영에서 DB 를 지우는 일은 없다.
